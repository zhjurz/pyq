

# kanle · Moments Blog

A WeChat Moments-style personal blog system supporting posts, articles, comment interactions, media uploads, R2 music playlists, Douban collections, RSS, and backend management.

Recommended deployment: **Vercel (frontend/backend separated) + TiDB Cloud / Managed MySQL + Cloudflare R2**, requiring no self-hosted application server; also retains VPS + PM2 + Nginx self-hosting options.

> All domains, database addresses, accounts, and keys in this document are placeholder examples. Please use your own real configurations, and **never commit `.env`, database passwords, R2 Access Keys, JWT secrets, or other Tokens to the repository**.

## Features

- **Moments/Feed**: Image/text, multi-image collages, videos, Live Photos, music, link cards, Douban cards, and geolocation;
- **Articles**: Rich text editing, cover images, tags, table of contents, archive timeline;
- **Comments/Interactions**: Threaded comments, reply collapsing, emojis, likes, email notifications;
- **Media & Music**: Direct media upload to Cloudflare R2, R2 audio playlists, LRC lyrics, floating player;
- **Douban Collections**: Sync movie, book, and music collections, with filtering and pagination;
- **Backend Management**: Posts, articles, comments, media, friend links, ads, music, blacklist, SMTP, Amap, Douban, RSS, and site settings;
- **UX & SEO**: Responsive layout, dark mode, RSS Feed, SSR, and OG tags.

# Recommended Deployment: Vercel + TiDB/Managed MySQL + Cloudflare R2

This setup deploys the frontend and backend as two separate Vercel projects:

```text
Browser
  │
  ▼
Vercel Frontend (frontend)
  │  Browser accesses /api/*; Next.js forwards requests server-side
  ▼
Vercel Backend (backend)
├──► TiDB Cloud / Managed MySQL (business data)
└──► Cloudflare R2 (images, videos, audio, and other media)
```

Prepare three stable origins:

| Purpose | Example | Description |
| --- | --- | --- |
| Frontend Site | `https://example.com` | The website users actually visit |
| Backend API | `https://api.example.com` | The Vercel backend project URL; can initially use Vercel's stable Production URL |
| R2 Media Domain | `https://media.example.com` | Public custom domain bound to the R2 Bucket |

Do not use Vercel Preview URLs generated by every build for long-term configuration. Preview URLs may change, which can break CORS, R2 uploads, and callback configurations.

## 1. Prerequisites

- GitHub or Gitee repository;
- Vercel account;
- TiDB Cloud or other publicly accessible MySQL-compatible database;
- Cloudflare account and R2 Bucket;
- Node.js 20+ and pnpm (used to initialize the target database locally);
- Optional: A domain hosted on Cloudflare for R2 media custom domain binding.

## 2. Create Database & Initialize

### 2.1 Create TiDB / MySQL Database

In the TiDB Cloud SQL Editor, cloud database console, or MySQL client, create a database, e.g.:

```sql
CREATE DATABASE moment_blog
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

Record the following information provided by the database service:

```text
Host
Port
Username
Password
Database name
Whether SSL/TLS is required
```

Managed services like TiDB Cloud typically require TLS; refer to the console's Connect page for details. Common configuration:

```env
DB_SSL=true
```

> `db:init` only initializes an **existing** database and does not execute `CREATE DATABASE`. If you encounter an `Unknown database` error, complete this step first.

### 2.2 Initialize the Target Database Locally

After downloading the source code, enter the backend directory locally:

```bash
cd backend
pnpm install
```

Copy the environment variable template:

```bash
# macOS / Linux
cp .env.example .env

# Windows PowerShell
# Copy-Item .env.example .env
```

Edit `backend/.env` to point to your target database. Example below:

```env
DB_HOST=<your-database-host>
DB_PORT=<your-database-port>
DB_USER=<your-database-user>
DB_PASSWORD=<your-database-password>
DB_NAME=moment_blog
DB_SSL=true

# Only used to create an admin when none exists yet
ADMIN_EMAIL=admin@example.com
ADMIN_USERNAME=admin
ADMIN_PASSWORD=<choose-a-strong-password>
```

Run the only official database initialization command:

```bash
pnpm db:init
```

`db:init` will:
1. Verify the database connection;
2. Create missing project data tables;
3. Supplement currently supported compatible fields;
4. Create missing site setting records;
5. Create a default music playlist;
6. Create an admin account if none exists.

This command is safe to run repeatedly: it will not delete business data, will not reset existing admin passwords, and will not use `alter` or `force` on existing data.

> For production deployment, explicitly run `pnpm db:init` locally, in CI, or in a trusted maintenance environment. Application startup and Vercel cold starts default to only connecting to the database, **not automatically executing DDL**. Do not use `DB_SYNC_ON_BOOT=true` as a standard production deployment strategy.

## 3. Configure Cloudflare R2

Vercel Serverless filesystems are not persistent. Production images, videos, audio, and other media must be saved using object storage like R2.

### 3.1 Create Bucket & API Token

1. In the Cloudflare Dashboard, go to **R2 → Create bucket**;
2. Create a bucket, e.g., `moment-media`;
3. Go to **R2 → Manage R2 API Tokens**;
4. Create an API Token with **Object Read & Write** permissions;
5. Save the following information, to be filled into backend environment variables later:

```text
Cloudflare Account ID
Access Key ID
Secret Access Key
Bucket Name
```

### 3.2 Bind Public Media Domain

In the Bucket settings, bind a stable public custom domain, e.g.:

```text
https://media.example.com
```

This domain must be used for both:

```text
Backend R2_PUBLIC_URL
Frontend NEXT_PUBLIC_MEDIA_ORIGIN
```

They must be exactly the same, without a trailing `/`:

```text
Correct: https://media.example.com
Wrong: https://media.example.com/
```

### 3.3 Configure R2 CORS

When browsers upload media, they directly `PUT` to R2 via pre-signed URLs issued by the backend. The R2 Bucket requires independent CORS configuration; the backend's `CLIENT_URL` or `CORS_ALLOWED_ORIGINS` cannot replace it.

Configure in **R2 → Bucket → Settings → CORS Policy**. Production template:

```json
[
  {
    "AllowedOrigins": [
      "https://example.com",
      "https://www.example.com"
    ],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag", "cf-ray", "x-amz-request-id"],
    "MaxAgeSeconds": 3600
  }
]
```

For local development, additionally add:

```text
http://localhost:3000
```

Note:
- `AllowedOrigins` should contain the **full Origin of the frontend page opened in the browser**;
- Do not include the API domain or R2 media domain unless the page is actually served from that origin;
- If testing with the frontend Vercel Production URL, add it as well;
- Do not use `"AllowedOrigins": ["*"]` in production.

## 4. Deploy Backend Vercel Project

Import the repository in Vercel and create the first project:

| Setting | Value |
| --- | --- |
| Root Directory | `backend` |
| Framework Preset | `Other` |
| Build / Output Settings | Use project defaults |

The project already includes `backend/vercel.json`, which configures Serverless Function rewrites and Douban sync Cron. Vercel automatically injects `VERCEL=1`, so no manual setting is needed.

Configure Production environment variables in **Settings → Environment Variables**.

### Backend Runtime Environment Variables

| Variable | Required | Example / Description |
| --- | --- | --- |
| `NODE_ENV` | Yes | `production` |
| `DB_HOST` | Yes | `<your-database-host>` |
| `DB_PORT` | Yes | Port provided by the database console; do not assume it's `3306` |
| `DB_USER` | Yes | Database username |
| `DB_PASSWORD` | Yes | Database password |
| `DB_NAME` | Yes | e.g., `moment_blog` |
| `DB_SSL` | Typically for managed DBs | Usually `true` |
| `DB_SSL_REJECT_UNAUTHORIZED` | Optional | Set to `false` only if explicitly required by the DB provider |
| `JWT_SECRET` | Yes | Independent random string, 32+ characters |
| `JWT_EXPIRES_IN` | No | Defaults to `7d` |
| `CLIENT_URL` | Yes | Stable frontend origin, e.g., `https://example.com` |
| `CORS_ALLOWED_ORIGINS` | Optional | Multiple stable origins separated by commas; takes precedence over `CLIENT_URL` |
| `REVALIDATE_SECRET` | Yes | Must exactly match the frontend同名 variable |
| `FRONTEND_REVALIDATE_URL` | Optional | Falls back to `CLIENT_URL` if empty |
| `CRON_SECRET` | Recommended | Independent random string protecting the Douban Cron endpoint, backend only |
| `R2_ACCOUNT_ID` | Yes | Cloudflare Account ID |
| `R2_ACCESS_KEY_ID` | Yes | R2 Object Read & Write Access Key ID |
| `R2_SECRET_ACCESS_KEY` | Yes | Corresponding Secret Access Key |
| `R2_BUCKET` | Yes | Bucket name |
| `R2_PUBLIC_URL` | Yes | Public media origin, e.g., `https://media.example.com` |
| `DB_POOL_MAX` | Optional | Serverless connection pool max; defaults are already tuned for Vercel |
| `DB_POOL_IDLE` | Optional | Connection pool idle eviction time (ms) |

Backend config example:

```env
NODE_ENV=production

DB_HOST=<your-database-host>
DB_PORT=<your-database-port>
DB_USER=<your-database-user>
DB_PASSWORD=<your-database-password>
DB_NAME=moment_blog
DB_SSL=true

JWT_SECRET=<a-random-secret-at-least-32-characters>
JWT_EXPIRES_IN=7d

CLIENT_URL=https://example.com
REVALIDATE_SECRET=<another-random-secret>
CRON_SECRET=<another-independent-random-secret>

R2_ACCOUNT_ID=<your-cloudflare-account-id>
R2_ACCESS_KEY_ID=<your-r2-access-key-id>
R2_SECRET_ACCESS_KEY=<your-r2-secret-access-key>
R2_BUCKET=moment-media
R2_PUBLIC_URL=https://media.example.com
```

`JWT_SECRET`, `REVALIDATE_SECRET`, and `CRON_SECRET` should use distinct random values.

> `ADMIN_EMAIL`, `ADMIN_USERNAME`, and `ADMIN_PASSWORD` are only used locally during the first `db:init` run when no admin exists in the database. They are not required runtime variables on Vercel after database initialization.

## 5. Deploy Frontend Vercel Project

Create a second Vercel project from the same repository:

| Setting | Value |
| --- | --- |
| Root Directory | `frontend` |
| Framework Preset | `Next.js` |

Configure in the frontend project's **Settings → Environment Variables**:

| Variable | Required | Example / Description |
| --- | --- | --- |
| `NEXT_PUBLIC_API_URL` | Yes | Fixed to `/api` |
| `BACKEND_URL` | Yes | Backend origin, e.g., `https://api.example.com`; do not append `/api` or trailing `/` |
| `NEXT_PUBLIC_SITE_URL` | Recommended | Public frontend origin, e.g., `https://example.com` |
| `NEXT_PUBLIC_MEDIA_ORIGIN` | Yes | Must equal backend `R2_PUBLIC_URL` |
| `REVALIDATE_SECRET` | Yes | Must equal backend `REVALIDATE_SECRET` |

Example:

```env
NEXT_PUBLIC_API_URL=/api
BACKEND_URL=https://api.example.com
NEXT_PUBLIC_SITE_URL=https://example.com
NEXT_PUBLIC_MEDIA_ORIGIN=https://media.example.com
REVALIDATE_SECRET=<the-same-value-as-backend>
```

The following must hold true:

```text
frontend.REVALIDATE_SECRET = backend.REVALIDATE_SECRET
frontend.NEXT_PUBLIC_MEDIA_ORIGIN = backend.R2_PUBLIC_URL
```

Do not use the following variables to store secrets:

```env
NEXT_PUBLIC_REVALIDATE_SECRET
NEXT_PUBLIC_CRON_SECRET
```

Any variable with the `NEXT_PUBLIC_` prefix will be exposed to the browser during frontend build.

### Why `NEXT_PUBLIC_API_URL` must remain `/api`

Browser request:
```text
https://example.com/api/posts
```
Next.js forwards server-side via `BACKEND_URL` to:
```text
https://api.example.com/api/posts
```
Therefore, do not set `NEXT_PUBLIC_API_URL` to the full backend address. Keeping it as `/api` reduces browser cross-origin cookie issues; API path changes are unnecessary when domains change.

## 6. Bind Domains, Preview & Redeploy

It is recommended to bind stable Production domains to Vercel:

```text
Frontend: https://example.com
Backend: https://api.example.com
R2: https://media.example.com
```

After binding, re-verify:

```env
# frontend
BACKEND_URL=https://api.example.com
NEXT_PUBLIC_SITE_URL=https://example.com
NEXT_PUBLIC_MEDIA_ORIGIN=https://media.example.com

# backend
CLIENT_URL=https://example.com
R2_PUBLIC_URL=https://media.example.com
```

After modifying environment variables, please perform a **Redeploy** for both frontend and backend projects.

Special note: `NEXT_PUBLIC_MEDIA_ORIGIN` is used during frontend build for Next Image remote domain whitelist. Changing the R2 media domain requires a frontend rebuild.

If testing Vercel Preview deployment:
1. Use a stable Preview URL, or record the actual full Preview Origin;
2. Add this Origin to backend `CORS_ALLOWED_ORIGINS`;
3. Add it to the R2 Bucket `AllowedOrigins` as well;
4. Do not rely long-term on Preview addresses that change with branches as production configuration.

## 7. Post-Deployment Checks

1. Access backend health check:
   ```text
   https://api.example.com/api/health
   ```
   Expected response:
   ```json
   { "status": "ok", "timestamp": "..." }
   ```
2. Open frontend site, confirm Network panel shows paths like:
   ```text
   /api/posts
   /api/settings
   /api/friends
   ```
3. Log in with the admin account created via `db:init`:
   ```text
   https://example.com/admin/login
   ```
4. Upload a test image or audio: confirm it uploads to R2 and is accessible via the media domain matching `R2_PUBLIC_URL`;
5. Publish a test post: confirm list refresh and page revalidation work normally;
6. If Douban collections are enabled, confirm the backend `CRON_SECRET` is configured, and check if your current Vercel plan supports Cron Jobs. If not, use an external scheduler to call this endpoint periodically.

# Optional: VPS + PM2 + Nginx Self-Hosting

If you prefer to maintain your own server, MySQL, Nginx, SSL, and process management, use the following setup. The Vercel method is recommended for new deployments; VPS mode suits scenarios requiring fixed egress IPs, LAN databases, or full server control.

## Prerequisites

- Debian 12 server (root or sudo privileges);
- A domain name (recommended);
- Cloud provider security group allows `80`, `443`, and `22` ports;
- Cloudflare R2 ready as persistent media storage.

## 1. Install System Dependencies, Node.js & PM2

```bash
apt update && apt upgrade -y
apt install -y curl wget git vim build-essential nginx mysql-server

# Install Node.js 20 LTS
curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt install -y nodejs

# Enable pnpm and install PM2
corepack enable
corepack prepare pnpm@latest --activate
npm install -g pm2
```

Verify:
```bash
node -v
pnpm -v
pm2 -v
```

## 2. Create Local MySQL Database

```bash
systemctl enable --now mysql
mysql -u root -p
```

Execute in MySQL:
```sql
CREATE DATABASE moment_blog CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'kanle'@'localhost' IDENTIFIED BY '<choose-a-strong-password>';
GRANT ALL PRIVILEGES ON moment_blog.* TO 'kanle'@'localhost';
FLUSH PRIVILEGES;
EXIT;
```

## 3. Clone & Deploy Backend

```bash
INSTALL_DIR=/opt/kanle

# Use Gitee for servers in China
# git clone https://gitee.com/ziln_cn/kanle.git $INSTALL_DIR

git clone https://github.com/zilinnb/kanle.git $INSTALL_DIR
cd $INSTALL_DIR/backend
pnpm install
cp .env.example .env
```

Edit `.env`. Set at least database, JWT, frontend origin, revalidation secret, and full R2 config:

```env
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=kanle
DB_PASSWORD=<your-database-password>
DB_NAME=moment_blog

JWT_SECRET=<a-random-secret-at-least-32-characters>

REVALIDATE_SECRET=<another-random-secret>

R2_ACCOUNT_ID=<your-cloudflare-account-id>
R2_ACCESS_KEY_ID=<your-r2-access-key-id>
R2_SECRET_ACCESS_KEY=<your-r2-secret-access-key>
```

Build, initialize, and start:
```bash
pnpm build
pnpm db:init
pm2 start ecosystem.config.js
pm2 save
```

Verify:
```bash
curl http://127.0.0.1:4000/api/health
```

Copy and edit the provided config:


# Upgrade & Maintenance

## Vercel / Serverless Upgrade

1. Backup the database before deployment;
2. Update repository code;
3. If the changelog mentions model or compatible field updates, run in a trusted maintenance environment with `.env` pointing to the target DB:
   ```bash
   cd backend
   pnpm install
   pnpm db:init
   ```
4. Redeploy frontend and backend projects in Vercel;
5. Check health endpoints, login, and media uploads.

`db:init` does not handle historical business data migration, R2 music migration, or like resets. Such scripts must be operated according to corresponding version notes, and databases should be backed up beforehand; do not treat them as initial installation steps.

## VPS Upgrade

```bash
cd $INSTALL_DIR
git pull

cd backend
pnpm install
pnpm build
pnpm db:init
pm2 restart kanle-backend

cd ../frontend
pnpm install
pnpm build
cp -r .next/static .next/standalone/.next/static

```

# FAQ

<details>
<summary>Do I need to rebuild the frontend after changing domains?</summary>

If `NEXT_PUBLIC_API_URL` remains `/api`, normal frontend domain changes usually don't require modifying client API paths; but if you change `BACKEND_URL`, `NEXT_PUBLIC_SITE_URL`, or `NEXT_PUBLIC_MEDIA_ORIGIN`, you should update environment variables and redeploy the frontend. Especially, changing the media domain affects the Next Image whitelist and requires a frontend rebuild.
</details>

<details>
<summary>Published post but page doesn't refresh?</summary>

Check if backend `REVALIDATE_SECRET` and frontend `REVALIDATE_SECRET` are exactly identical. This is a server-side secret and should not have the `NEXT_PUBLIC_` prefix.
</details>

<details>
<summary>R2 upload fails, CORS error, or images won't display?</summary>

1. Confirm backend has complete R2 environment variables configured;
2. Confirm `NEXT_PUBLIC_MEDIA_ORIGIN` exactly matches `R2_PUBLIC_URL`;
3. Confirm R2 Bucket CORS includes the current frontend's full origin, and allows `PUT`, `GET`, `HEAD`, and `Content-Type`;
4. `403` during PUT phase usually relates to R2 credentials, signatures, or Content-Type mismatch;
5. Confirm phase failures usually relate to object MIME, size, or copy permissions;
6. In Vercel environments, media flows through `presign → browser direct PUT to R2 → confirm`. Do not revert to uploading large files via Vercel functions.
</details>

<details>
<summary>TiDB / Managed MySQL connection fails?</summary>

Confirm `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` match the provider's Connect page. Managed services like TiDB Cloud typically require `DB_SSL=true`. Only set `DB_SSL_REJECT_UNAUTHORIZED=false` if explicitly required by the provider.
</details>

<details>
<summary>Why can't the database be auto-initialized on Vercel cold start?</summary>

Multiple Serverless instances may cold start simultaneously; if each executes DDL, connection and table creation conflicts can occur. Explicitly run `pnpm db:init` before deployment or during maintenance. Do not use `DB_SYNC_ON_BOOT=true` as standard production configuration.
</details>

<details>
<summary>Amap search or reverse geocoding occasionally returns 502?</summary>

Backend Amap Web Service requests originate from Vercel Serverless dynamic egress IPs. If your Amap Web Service Key is bound to a fixed IP, you may experience intermittent failures. Confirm the backend uses a "Web Service" type Key, and unbind the IP or use a proxy with a fixed egress IP based on security needs; do not fill the Web JS API Key into the backend Web Service Key field.
</details>

<details>
<summary>Forgot admin password?</summary>

Set a new `ADMIN_PASSWORD` in the backend runtime environment, then run:
```bash
cd backend
node dist/scripts/reset-password.js
```
This admin command resets the corresponding admin's password to the current `ADMIN_PASSWORD`.
</details>

# Local Development

```bash
# Backend
cd backend
pnpm install
cp .env.example .env
# Edit .env and point to an existing local/test database
pnpm db:init
pnpm dev
```

Open another terminal:

```bash
# Frontend
cd frontend
pnpm install
cp .env.example .env.local
pnpm dev
```

Both initial development and production deployment require explicitly running `pnpm db:init`; the application does not automatically alter database table structures on startup.
